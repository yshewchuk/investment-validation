## Workspace artifacts

- Except for ops-store attempt staging assigned to the supervisor below, put disposable scratch, spills, transient staging copies, and intermediate outputs that no process reads after the producer exits under `/tmp` or a dedicated directory named `scratch`, `tmp`, or `disposable`, outside durable-data trees.
- Keep durable outputs, including catalogs, content-addressed objects, evidence, and the ledger, in their established locations.
- Tools that create scratch remove it on success; on failure, they remove all scratch contents except diagnostics and leave those in the disposable scratch location.
- Agents remove their worktrees when merged or abandoned; the supervisor also removes merged worktrees with no uncommitted changes.
- The supervisor manages and reclaims ops-store attempt staging as specified in [#609](https://github.com/yshewchuk/investment-validation/issues/609); this overrides the placement and cleanup rules above for that staging.
- Agents never hand-delete under an ops store and report cleanup needs to the supervisor.

## Pull requests, gates and owners

- The PR watcher runs the merge gate. It starts detached, once per head (a head that already has a merge-gate status is not re-gated), as soon as no finished required check is failing, no review thread is open, no CodeRabbit review is in progress on that head and the owner's session has exited; it does not wait for CI to finish or for CodeRabbit approval. It runs at most 40 automatic launches per PR (the merge-train PR is exempt), plus one per `gate-extra-round` label, which only the user or supervisor applies. Owners do not run the gate.
- CodeRabbit is asked only for gate-passed, CI-green PRs it has never reviewed, oldest gate pass first. It approves from the thread conversation, which lets the PR merge without a train. When it requests changes, the owner replies in every CodeRabbit thread (`fixed in <sha>`, `deferred to #N`, or a dispute with evidence) and never fixes silently; the gate re-runs after the push. If CodeRabbit still does not approve, the PR becomes a merge-train car (label `train-car`): once gate and CI pass, it is squashed onto the open merge-train PR. Expect 12+ hours, so self-review hard before the first attempt.
- The merge train is one open PR on a `merge-train/*` branch with the label `merge-train`. It gets CodeRabbit priority at 6 cars or 12 hours after its oldest car boarded, and keeps it until it passes. Its merge gate is a mechanical check (every commit is a car squash of a gate-passed head, or a revert of one), not the model gate. When a CodeRabbit thread on the train implicates exactly one car, that car is reverted off it until its fix passes the gate again; with zero or several implicated cars the train escalates to the supervisor and reverts nothing. The train merges by rebase, so each car lands as its own commit; car PRs are then closed with a link.
- The gate has two tiers. A cheap tier of independent reviewers runs first; if it finds any Must fix item the run stops there, otherwise the expensive tier runs. One launch covers both tiers. Reviewers rate each finding (accuracy, likelihood, impact); the gate sorts findings into three tiers by rules in code that owners do not see:
  - **Must fix**: any one makes the gate BLOCK(n), n = the number of Must fix items.
  - **Should fix**: does not block merge.
  - **Consider fixing**: does not block merge.
- Merge (the repository ruleset) requires the `test` and `merge-gate` checks and one approving review. Thread resolution is not a ruleset requirement, but open threads hold the gate.
- Owners wake for a BLOCK, for one polish round, after a MERGE-READY with nothing left to polish (a clean first pass, or the polish re-gate) to request merge, and when a merge request fails the merge check. Polish round (required): after the first gate MERGE-READY whose verdict lists Should or Consider items, the owner is woken once, fixes the quick, low-risk, small items and pushes once (a normal full re-gate). If nothing is worth polishing, say so in Gate notes.
- Merge request: owners never merge and never arm auto-merge. Before merging, if the final head has unaddressed gate Should items or deferred CodeRabbit findings, the owner files ONE GitHub issue listing them and links it in the disposition table; otherwise no issue is needed. The owner then adds the label `merge-request`. The watcher then runs a cheap-model merge check that every unaddressed finding that needs an issue (not skipped Consider items) is in a linked issue. On pass it merges; on fail it comments the missing items, removes the label and wakes the owner. Any new push removes the label; re-request after the re-gate.
- Gate findings come from automated reviewers and may be wrong or rest on unrealistic scenarios. Verify each against the current code and fix only real issues in realistic scenarios. Dispute an invalid or unrealistic finding in Gate notes with evidence (file:line, the caller or input that rules it out); the next round re-checks it. The gate files one GitHub issue for each out-of-scope finding; reviewers do not.
- Owner rule for a pushing round: fix every Must fix item. Fix Should fix items in the same push unless doing so would drastically grow the PR's scope; then skip the item, file an issue for it, and give the issue link and the reason in Gate notes. Fix a Consider fixing item only if it takes 1-2 lines; a skipped Consider fixing item needs no issue. Never defer a Must fix item without the gate's agreement.
- On a BLOCK, fix real findings and push once per round. Continue independently until the launch cap, then stop and report. Deferring a finding to an issue requires the gate's agreement, as with a CodeRabbit comment. If the gate blocks on it again, fix it.
- Every PR description starts with `## Gate notes` (about 1,000 characters maximum; the gate reads the first 4,000 description characters). Keep concise round notes there, plus a disposition table: every Should item of the latest gate verdict and every CodeRabbit thread, each marked `fixed <sha>`, `deferred #<issue>` or `disputed (<link>)`. Update the notes before each fix push. The gate takes no notes file.
- Before writing a PR Spec, check whether a standard tool or library covers the need (see the "Hand-rolling a standard format or tool" anti-pattern in `ARCHITECTURE.md` §6), and name it in the Spec or say why not. If review findings land on standard-format edge cases for two rounds, re-check whether a usable maintained tool covers them. Propose that tool when it does; otherwise document in the Spec why the custom implementation remains necessary.
- Size limits count added lines only: code PRs, about 400 non-test code lines and 120 doc lines; design PRs, about 300 doc lines and a split list. Deleted lines do not count; a category with zero or negative net change is never size-blocked. A PR within limits at its first reviewed head is not size-blocked when the overage is review- or gate-found bug fixes. For scope growth over a limit mid-work, stop and split (add, then wire, then remove).
- A comment from the shared GitHub login that starts with `@pr-owner` force-wakes that PR's owner, bypassing the wake gap and hourly cap. This is the user's lever; owners never start their own comments with it.
- Owner tooling (watcher, gate, owner scripts and metrics) lives outside this repository.
- Before the first push of a PR that edits an `ARCHITECTURE.md`, run `python3 tools/oc_check.py tests/test_architecture_doc_budgets.py`.
- To update a PR description, write a Markdown file and run `gh pr edit <n> --body-file <file>`. Do not use an inline script that writes files.
- New tests go in `tests/v2/<package>/` (package names from `checks/layer_map.py`) or `tests/v2/integration/`, never the root `tests/` folder. A PR that edits a root-level test should move it and lower `checks/test_layout_budget.txt` by exactly the number of files moved. Before pushing, run `python3 checks/test_layout_budget.py --base-ref origin/main`; PR CI enforces it.
