# SIZE derived feature sets: log copies (L) and log copies + pairwise products (LP) (design)

Design only; nothing is built. Same pattern as `guides/size_feature_groups_design.md` (pure computation, then recipe, then request binding, then wiring, then contract promotion into `engine/v2/research/ARCHITECTURE.md`). User request 2026-11-14: two sets adjacent to `HMOSX`, so the next official run compares `HMOSX`, `HMOSX+L` and `HMOSX+LP` as separate arms and the existing selection chooses: inner-year pooled RMSE when the request has no `selection` block, otherwise the request's weighted inner-pooled blend (`size_search_binding.py:313-319`).

**Evidence (exploratory, not promotion evidence).** the supervisor's 2026-11-14 exploratory scripts and outputs (`feat4.py`, `f4.out`; kept outside this repository): 11 yearly folds 2014-2024, no 2025, a 63-column HMOSX-like base, ElasticNet (alpha .03, l1 .25). L (42 `log1p` copies in the scratch, raw kept): RMSE -0.31%, MAE -0.43%, better 11/11 on both. LP (L + 28 products): RMSE -0.36%, MAE -0.40%, 11/11 vs base; the increment over L alone is weak (RMSE 7/11, MAE 4/11), so L and LP are separate arms. HGB gains nothing (RMSE -0.00%; scale-invariant); the sets still apply to every family so arms stay comparable. The script reads parquet and is a definition reference only. The panel has 73 columns, not 63, and the fixed list below has 39 columns, not 42, so the effect size only approximately transfers; the official run is the confirmation.

## 1. Where the derived columns live

| | (a) New panel columns | (b) Derived at load/fit time from stored columns |
| --- | --- | --- |
| Panel | table `.v5` to `.v6`, 67 more float64 columns, full rebuild (~11 h, a heavy job needing its own authorization); sealed v5/v11 panels are discarded; row ids, contexts, snapshots all move | unchanged: table `.v5`, context `.v5`, `feature_recipe` `HMOSX`; the v11 panel is reused |
| Identity | in the panel dictionary hash | in the candidate's recipe dictionary hash (below) |
| Changing the list or a transform | another rebuild | a recipe change only |
| Cost | storage and rebuild; no per-run compute | derived in the worker, on load of each fold's stored input and before the fit (not at panel build). `fold_inputs` (`size_search_binding.py:357`) reads the panel per fold and persists the participant rows as the worker input; that input keeps only stored columns, so `stored_inputs_id` is unchanged and shared by all arms. One vectorised pass per fold and candidate: fold rows x 67 x 8 B (39 logs plus 28 products), reported at the stage boundary |
| Duplicated source of truth | stored value could in principle disagree with recipe | none: values are never stored |

**Decision (supervisor's judgement, adopted because it holds up on the three conditions below): (b).** Every transform is a pure row-wise function of stored columns, and the next run can reuse the v11 panel.

Conditions, stated exactly:

1. **Identity.** A derived set is a *model-feature recipe over the panel*, not a panel subset. `recipe("HMOSXL")` / `recipe("HMOSXLP")` in `magnitude_panel_qualified_table.py` return the `HMOSX` dictionary plus derived fields. Each derived field carries `source_dependencies: [{role: "panel_column", name}]` and `derivation_policy: {schema_version: "derived_feature.v1", function: "log1p"|"product", sources: [...]}`, float64, nullable, `on_missing: null`, unit `log1p(<unit>)` or `<u1>*<u2>`. These sit in `dictionary`, so they enter `dictionary_hash`, `model_columns` and `candidate_spec_id`, and the request id binds the hash (section 3). Derived recipes add `base_subset: "HMOSX"` and a derivation marker; the v1-v11 recipes gain no key, so their hashes and every v1-v11 request id stay byte-identical.
2. **Provenance.** Stored inputs are pinned by the snapshot id and `context_id` (unchanged); the function is in the registered `source_closure`; the dictionary pins which function and sources produce each column. Value = f(pinned stored value, pinned policy, pinned code), and nothing derived is persisted that could drift from that. Determinism is claimed per pinned environment (float64 `numpy.log1p` and multiply), as for the fits themselves.
3. **Stored-panel contract.** The panel build and the registration validator keep calling `recipe("HMOSX")`; the context `feature_recipe` stays `HMOSX`. `recipe()` gets a guard so a derived subset passed as a panel recipe refuses `CONTRACT_MISMATCH`. The panel read requests the stored columns only (`recipe("HMOSX")["model_columns"]`), identical for all arms; `_panel_columns` must not forward derived names to `read_panel`.

Standard tools: `numpy.log1p` and `*` are used directly. `sklearn` `PolynomialFeatures(interaction_only=True)` would form all C(73,2) products and `FunctionTransformer(np.log1p)` would hide the transform in estimator params; neither gives a fixed named list in the dictionary hash, and both would run per fit. Not used.

## 3. Names, request binding, candidate counts

Set names: `HMOSXL` (HMOSX + 39 logs) and `HMOSXLP` (HMOSXL + 28 products). The letters extend the existing superset-name scheme; `HMOSXLP` is a strict superset of `HMOSXL`, which is a strict superset of `HMOSX`.

- **Request `v12`** (the next free version: `guides/size_ensemble_design.md` also names v12, so whichever merges second takes v13 and slice 3 uses the next free number) requires the `HMOSXLP` dictionary hash (the widest superset, as `HMOSX` was for v11) and allows `H/HM/HMO/MO-/M/HMOS/HMOSX/HMOSXL/HMOSXLP` in that order. v11 and earlier behave exactly as today (`HMOSXL*` in a v11 request is refused as an unknown set).
- `size_search_binding._panel_subset` today maps version to one subset used both for the dictionary-hash check and for the panel read. It splits into two: dictionary subset (v12: `HMOSXLP`) and stored-panel subset (v12: `HMOSX`).
- **Candidate counts.** Unchanged formula `len(feature_sets) * G + (1 if HMO in sets)` (`G` is the per-set grid size, the product-sum of the non-size family axes). The 1000-candidate ceiling in `experiments/magnitude_search_request_v3.py:218-225` applies to the **total** count, so it shrinks the room for `G`: three arms need `G <= 333`, four `G <= 250` (one lower when `HMO` is among the sets, as the `size_v1_4` candidate counts one). A request that exceeds it is refused at compile time. The intended official comparison `[HMOSX, HMOSXL, HMOSXLP]` is `3G`; with `HMOS` kept as a reference arm `4G`. Fits scale the same way. HGB-family candidates on L/LP are expected to tie the base within noise; that cost is accepted because the user asked for the sets on every family. No per-column ablation is promised.

## 4. Failure semantics

Pure function `derive_columns(columns, set_name)` takes a mapping of column name to a 1-D float array (NaN is a null) and returns the derived columns in recipe order. Rules:

| Case | Result |
| --- | --- |
| Source value is null | derived value null (a product is null if either input is null). Never zero-filled |
| Negative input to `log1p` (the panel's non-negative contract is violated) | `CONTRACT_MISMATCH`; no clip (the scratch skipped any column with a negative value; it did not clip). Not reachable from a conforming panel, since every listed column is >= 0 by definition or range check |
| Non-null `+-inf` input | `CONTRACT_MISMATCH` |
| Non-finite result from finite input (product overflow) | `EXPERIMENT_VARIANT_FAILED`, as the HMOSX groups |
| Source column absent from the frame, wrong length, or non-float dtype | `CONTRACT_MISMATCH` (a wiring error, not data shortage) |
| Source is an X column and the projection was not admitted by `admit_columns(..., x_groups=True)` | refused earlier by the read, `HOLDOUT_ACCESS_DENIED`; the derive step only sees admitted frames |
| Unknown set name, or a request/recipe whose derived fields differ from the installed lists | `INVALID_EXPERIMENT_SPEC` at request compile (v12 dictionary-hash gate, as the v11 gate in `magnitude_search_request_versions.py:50-52`); a request/recipe hash differing at binding time is `EXPERIMENT_IDENTITY_CONFLICT` (`size_search_binding.py:129`) |
| Legitimate shortage | null, never a refusal |

**`on_missing` and imputation.** Derived columns declare `on_missing: null`. The fit recipes already impute by the recipe, not per column: Ridge/ElasticNet/MLP use median imputation fitted on training rows with `missing_indicator: all` and standard scaling; HGB uses native missing handling. A derived column's null set is the union of its sources' null sets, so its missing indicator duplicates a source indicator (or is a union of two for a product). Decision (mine, for review): keep the recipe's uniform `indicator: all` and add no special case. The effect is `output_features` (Ridge/ElasticNet) or `union_features` (MLP, which then keeps only training-nonconstant columns) growing from `2 x 73` to `2 x 112` (HMOSXL) and `2 x 140` (HMOSXLP) with perfectly collinear indicators, which the penalty and scaler tolerate; excluding them would add a per-column preprocessing rule to every family recipe validator. Materiality is measured: the first data run reports per-column derived null counts on stderr (one line, never per row).

## 5. Causality

Each derived value is a function of the same row's stored columns only: no other row, ticker, date window or fitted statistic enters (the transforms have no parameters estimated from data; the L list and the pair list are constants). Availability is therefore the intersection of the sources' availability, and every source is already causal at the row's decision date (the forecast clock's `source_session_ceiling`, by data date, never `computed_at`; the HMOSX contract in `engine/v2/research/ARCHITECTURE.md`). That is sufficient: a function of causal inputs that adds no inputs is causal, and because it uses no training statistics, applying it to each fold's rows (training and evaluation alike) cannot leak across folds. Holdout exclusion is inherited: the derive step runs on the frame the read already restricted to the admitted event ids; it opens no source and reads no holdout or outcome data. Only the median imputer and scaler remain fit-time, and they are already fitted on training rows per fold.

## 6. Third arm: spline basis (`spline_knots`)

User decision 2026-11-15: the next official SIZE run gets a spline arm. A cubic B-spline basis with quantile knots on the skewed columns is **a fitting step inside the ElasticNet recipe**, not stored panel columns and not a derived column of section 1, because knots are learned per training window. Ridge, HGB and MLP do not get it: HGB is scale-invariant (section header evidence), MLP has no screen, and Ridge was not screened. Another family later means a new request version.

**Evidence (exploratory, supervisor scratch, not promotion evidence).** 11 yearly folds 2014-2024, no 2025; ElasticNet l1 .25; base `HMOSXL`-like (HMOSX-like plus 42 `log1p` copies); `SplineTransformer(knots='quantile', include_bias=False)` on the 42 raw skewed columns the L set logs, fitted on training rows after median imputation and appended (raw and logs kept); 165 fits, 0 nonconverged. Same-alpha effect at alpha 0.1 (RMSE, years better / MAE, years better): 4 knots -0.13% (10/11) / -0.24% (8/11); 6 knots -0.16% (10/11) / -0.29% (8/11); 8 knots -0.16% (10/11) / -0.34% (8/11); top-10 columns only, 6 knots, -0.10% / -0.18%. At alpha 0.03 the gain is about half; at alpha 0.01 every spline arm is worse (overfit). The panel list below has 39 raw columns, not 42 (section 2), so the size only approximately transfers; the official run is the confirmation. The gain is small and unproven beyond these folds: a recipe with its own axis lets the run show it or drop it.

Two numerical findings are binding:

1. **`include_bias=False` is required.** The default B-spline basis sums to 1 per column, exactly collinear with the intercept (and with the other columns' bases summed). It is a declared recipe field and a validator-pinned constant.
2. **The pinned ElasticNet recipe cannot fit this width.** `magnitude_elasticnet_recipe.py` has `precompute: False`, `max_iter: 10000`, `nonconvergence: variant_failure_no_retry`, `numerical_threads: 1`. Without the Gram matrix, coordinate descent on about 500 correlated columns was measured about 100x slower (55 s versus 0.5 s per 5,000 iterations at 40k rows x 525 columns), and a scratch run with the defaults did not finish one year in 4.7 h. In the official pipeline that is hours per fit and probably nonconvergence variant failures. The spline recipe therefore declares `precompute: True`; section 6(d) decides where.

### (a) Position and shape

The step is fitted on the training rows of each fold and horizon only, like the imputer and scaler (`fit_scope: fold_and_horizon`). Today the ElasticNet pipeline is `FeatureUnion([median imputer, missing indicator])`, scaler, estimator (`_magnitude_elasticnet_estimator.py`). The step sits on the imputer branch: imputer, then a `ColumnTransformer` that passes every imputed column through and appends `SplineTransformer(n_knots=k, degree=3, knots="quantile", extrapolation="constant", include_bias=False)` fitted on the selected columns. The missing indicator still runs on the original columns, so indicators stay one per original column; the scaler then standardises raw, log and basis columns together. The basis needs finite values, hence after imputation (`keep_empty_features` gives an all-null training column the constant 0, a single distinct value; see (c)).

- **Standard tool.** `sklearn.preprocessing.SplineTransformer` and `ColumnTransformer` are used directly. Hand-rolling a B-spline basis is not justified; the only custom code is the distinct-knot check and the recipe block.
- **Width.** Each selected column adds `k + degree - 2 = k + 1` columns (`k + degree - 1` basis functions minus the dropped bias function): 7 at `k = 6`. With 39 selected columns and `HMOSXL` (112 model columns, so 224 imputer plus indicator outputs) that is `224 + 39 x 7 = 497` estimator inputs; `output_features` in the recipe is that computed number.
- **Knots and extrapolation.** Knots are training-row quantiles of the imputed column; evaluation rows use the stored knots and never set them. `extrapolation: constant` (the sklearn default the screen ran) holds the basis at its boundary value outside the training range; the raw and log columns still carry the linear signal there. Other rules were not screened and are not offered.
- **Fixed, not axes:** degree 3, quantile rule, `constant` extrapolation, `include_bias: false`, the column list, and the "append, keep raw" output. Only `k` varies (6(b)).

### (b) Identity

- **Columns.** The 39 raw source columns of section 2's L list, as one literal constant `SPLINE_COLUMNS` in the models layer (the spline recipe module), not imported from the research layer (`derived_features`), which sits above models and training. A test in a layer that may import both asserts it equals the L list's source columns, so there is one list and no per-run rule over data. The three scratch columns without a panel equivalent are not replaced. No top-10 or other ablation is promised.
- **Recipe.** A `preprocessing.spline` block: `{columns, n_knots, degree: 3, knot_rule: "quantile", extrapolation: "constant", include_bias: false, input: "imputed", output: "append"}`. It sits inside the recipe built per candidate at binding, so it enters `candidate_id`. Learned knot values are fit outputs, never identity, like the imputer medians.
- **Request.** One new optional ElasticNet axis `spline_knots` (integers; `0` means no step, and then the recipe is today's recipe, byte-identical). A spline candidate's `parameters` carry `{alpha, l1_ratio, spline_knots}`, and `candidate_spec_id` hashes the request id, family, feature recipe and `parameters` (`magnitude_search_request_versions.py:76`), so the axis reaches both `candidate_spec_id` and the request id with no change to that hash. Allowed values: `0` or an integer in 4..8 (the screened range), strictly increasing like the other axes. `candidate_recipe` (`experiments/magnitude_candidate_recipe.py`) accepts the third key only when the request version allows it.
- **Version.** Request `v13`. `v12` and earlier refuse `spline_knots` (`INVALID_EXPERIMENT_SPEC`), so every v1-v12 request id and candidate id stays byte-identical. `v13` requires the same `HMOSXLP` dictionary hash as `v12` and the same set order; the spline columns are a recipe block, not dictionary fields, so the dictionary hash does not move. A `v13` request with no `spline_knots` axis equals the `v12` space.
- **Optional `ridge` family (user decision 2026-11-15: Ridge is dropped from the next official run).** From `v13`, `space` may omit `ridge`; `elasticnet`, `hgb`, `mlp` and `size_v1_4` stay required, and no other family becomes optional. Today `v>=9` requires `set(space) == set(families)` (`magnitude_search_request_v3.py` ~line 132); `v13` requires `set(space)` to be the closed family set minus an optional `ridge`, and the per-family loop skips an omitted family. A present `ridge` grid is validated exactly as today and grid values are unchanged. An omitted family contributes 0 candidates: the count formula of section 3 sums over the families present, `len(feature_sets) * sum_{present f} |grid_f|` plus the `size_v1_4` term, so omitting `ridge` removes `len(feature_sets) * |ridge grid|` candidates and the same share of fits. Identity: the request body (`space`) differs, so the `v13` request id differs from a request that carries `ridge`, and `candidate_spec_id` (which hashes the request id) moves with it; no candidate spec is emitted for an omitted family, and a surviving candidate's own recipe and `parameters` are unchanged. `v1`-`v12` requests keep requiring `ridge` (an omitted `ridge` there still refuses `INVALID_EXPERIMENT_SPEC`), so every v1-v12 request id and candidate id stays byte-identical. A request with `ridge` present and no `spline_knots` axis still equals the `v12` space apart from its `schema_version`.
- **Set composition.** A `spline_knots > 0` axis is accepted only for sets that contain all 39 selected columns: `HMOSX`, `HMOSXL`, `HMOSXLP` (smaller sets lack them: `INVALID_EXPERIMENT_SPEC` at compile, never a silent subset). The screen used the `HMOSXL` shape, so only `HMOSXL` has spline evidence; the other two are allowed and untested. Which sets the run pairs with the axis is the grid decision and is not made here.
- **Counts.** The ElasticNet sub-grid becomes `|alpha| x |l1_ratio| x |spline_knots|` (each non-spline arm is the `0` value); the formula in section 3 and the 1000-candidate ceiling apply to the total as before. The axis only multiplies ElasticNet candidates on the sets it applies to, so a request lists `spline_knots: [0]` or omits it for the rest. The alpha axis must reach 0.1 for the arm to be tested where it helped (0.3 worth considering; alpha 0.01 was worse with every spline arm); the existing bounds (1e-6..1000) already allow this and the design adds no alpha rule.

### (c) Failure semantics

| Case | Result |
| --- | --- |
| Selected column has fewer distinct training-row quantile knots than `n_knots` (ties at a boundary, constant column, all-null training column) | `EXPERIMENT_VARIANT_FAILED`, no retry, recorded for that fold and horizon. The check runs on the imputed training column before `SplineTransformer.fit`, using the same percentile rule. No silent thinning or per-fold knot count: that would give different realised features under one candidate identity |
| Non-finite basis output from finite input | `EXPERIMENT_VARIANT_FAILED` |
| ElasticNet reaches `max_iter` (convergence warning) | `EXPERIMENT_VARIANT_FAILED`, no retry (existing `nonconvergence` rule, unchanged) |
| A selected column missing from the frame or recipe, or `n_knots` / column list differing from the installed constants at validation | `CONTRACT_MISMATCH` at the recipe validator or `INVALID_EXPERIMENT_SPEC` at compile |
| Null prediction-row value | imputer first, so not a spline failure |

Quantile ties are the main design risk: several selected columns are likely to carry mass at one value (for example a share above a threshold with many zeros), and with `k = 6` the knots sit at the 0, 20, ..., 100th percentiles, so more than 20% of training rows at one value duplicates a knot. The scratch ran 165 fits without reported failures, which does not say whether sklearn tolerated duplicate knots or none occurred; that is not established. Slice S1 therefore measures the distinct-knot count per selected column and fold on the stored v11 panel in a read-only fixture test (no heavy job). If a listed column ties at the knot counts of the axis, the fix is a recipe-constant change to `SPLINE_COLUMNS` made in S1 with the reason recorded, never a per-fold fallback; the refusal stays as the guard.

### (d) Solver: `precompute: True`, spline recipe only

Decision (recommended and adopted): a new recipe `magnitude_elasticnet_spline_recipe.v1` with `precompute: True`, built by its own function next to `elasticnet_recipe`; the existing `elasticnet_recipe` (`precompute: False`, schema `.v1`) is unchanged, so every v1-v12 hash and non-spline candidate stays byte-identical. Reasoning: `precompute` changes the solver path; the optimum is the same within `tol` but results are not bitwise equal, so flipping the default would change every existing `candidate_id` and fit and break comparison with sealed runs. Everything else is copied unchanged (`max_iter: 10000`, `tol: 1e-4`, `selection: cyclic`, `warm_start: False`, `random_state: 0`, `numerical_threads: 1`, `nonconvergence: variant_failure_no_retry`); the validator rebuilds the recipe from `(columns, hash, alpha, l1_ratio, n_knots)` and refuses any other value as it does today. `spline_knots: 0` uses the old recipe.

Memory: the Gram matrix is `p x p` float64, about 2 MB at `p ~ 500`, plus `X^T y`; its build is O(n p^2) (about 10^10 operations at 40k rows). That replaces the per-iteration pass over the 40k x 500 matrix, which is why 5,000 iterations take about 0.5 s instead of 55 s (measured). Fit time of the first spline fit is measured and logged, not assumed. One v11 candidate (HMOSX ElasticNet alpha .001, l1 .25) failed in both inner years; its cause is **not established**, and `precompute` is not claimed to affect it. The spline recipe does not change the non-spline candidates, so that behaviour is not touched here.

### (e) Resource rules for the step (R1-R6)

R1 memory: a fold matrix of 40k rows x 497 columns x 8 B is about 160 MB per copy, with a few copies live in one fit (imputer branch output, union, scaled, `copy_X`), plus the 2 MB Gram; released after each fit, no growth with candidate count; one RSS line at the first fit boundary of the run. R2 nothing cached across fits or runs (knots and Gram are per fit). R3 refusals above. R4 nothing persisted (no store write). R5 no retry. R6 equal pinned stored inputs, code, sklearn and numpy give equal fits and equal recipe hash. Progress: the existing fit-stage line gains `spline_knots`, estimator input width and elapsed fit time; the end-of-run summary counts spline variant failures by reason (ties, nonconvergence); no per-row logging.

## 7. Resource and progress rules

R1 memory: fold rows x (up to 67) x 8 B per derive, plus the stored frame and one temporary column; released after each fit, no growth with candidate count; a measured RSS line at the derive boundary. R2 nothing cached across runs. R3 refusals above. R4 nothing persisted (no store write). R5 no retry. R6 equal pinned stored inputs, code and numpy give equal values and equal recipe hash. Progress: one stderr line per run (stage start/end with elapsed time, rows, derived column count, per-column null counts, RSS); no per-row logging.
