# Authority fence and switch/rollback protocol (P7-3, #739)

Design, not yet implemented. Source: `guides/rearchitecture_phase7_cutover.md` (P7-3, "Switch and rollback protocol"); `guides/rearchitecture_phase8_post_cutover.md` 8A entry. `engine/v2/ops/ARCHITECTURE.md` is over the 1000-line ceiling (frozen for growth), so the contract lives here until each slice folds its part in. No tool in this design switches production by itself: the activation step needs the standing session authorization and deployment permission (P7-5). Every drill below is supervisor-run against a scratch or private target (heavy jobs serialize; owners never run them).

**Decisions (owner, 2026-10-14, #739, not reopened).** The rollback window is **10 completed sessions** after the switch, mirroring P7-2. This decision sets the rollback retention window that `guides/rearchitecture_phase7_cutover.md` leaves to the release runbook, and it overrides that guide's "avoid another ten-session wait after a successful switch" for rollback retention only (that sentence is about qualification, not retention); the P7 guide is amended accordingly in this PR (both the qualification sentence and the retention-duration sentence). 8A may delete the legacy tree only after the tenth completed session has been verified. Legacy catch-up inside the window is specified in "Legacy catch-up".

**Standard tools.** Nothing here is a standard-format problem. The backup, restore, pointer primitives and the v2 `set_authority` compare-and-swap already exist and are reused; the legacy `authority.json`/`authority.lock` fence is new (slice 1b); the only new state is the legacy authority record and one receipt format (JSON, hash-checked like the P7-1 manifest). A distributed lock service or external lease library is not needed: there is one host and one SQLite catalog, and on the v2 side the fence is a row in the same catalog transaction as the writes it guards (the legacy side is a file plus `flock`, below).

## Invariant and fence

**At most one official writer (exactly one once the switch completes; zero during a held or interrupted switch).** At any instant at most one deployment (`legacy` or `v2`) may commit an official decision, settlement, ledger row, export or consumer-visible release. The fence is the existing `decision_authority` singleton in the v2 catalog (`engine/v2/ledger/decisions.py`: `owner`, `generation`, `switched_at`; `set_authority(conn, expected_owner, owner, stamp)` is compare-and-swap on `owner` and increments `generation`). It is extended, not replaced:

1. **Authority generation.** Every official commit path (`decision_commit`, outcome settlement, publication of a release that moves a consumer pointer) reads `decision_authority` inside its own write transaction and refuses unless `owner == "v2"` and the generation it was started with equals the current one (captured when the job record is created, carried in the record, and compared again inside the commit transaction). A writer started under generation N therefore cannot commit after generation N+1 exists, even if its process survived (a "zombie").
2. **Writer lease on the legacy side.** The legacy deployment has no catalog. Its lease is two files in the retained legacy data root: a stable coordination lock `authority.lock` (never replaced or renamed) and `authority.json {owner, generation}`. Every legacy writer takes a shared `flock` on `authority.lock`, reads `authority.json`, checks `owner == "legacy"`, and holds the lock through its guarded ledger appends. `fence`/`grant` take the exclusive lock, so they wait for in-flight writers and block new ones, then replace `authority.json` by atomic rename (safe because the lock lives on the separate file). The scheduler wrapper reads the generation from `authority.json` at each start, not from its environment, so a grant needs no scheduler reconfiguration. Reads of `authority.json` (wrapper at each start) and of receipts (readiness checker, `status`) are no-follow, regular-file only and byte-capped (64 KiB per receipt: receipts hold counts and content hashes only, and the S2b divergence list is stored as a separate hashed artifact the receipt references); a missing, oversize, non-regular or malformed file refuses with typed `AUTHORITY_FILE_INVALID` (the wrapper then does not run: fail closed). `authority.lock` is opened no-follow and regular-file only. Lock acquisition by `fence`/`grant` is bounded (default 300 s): on timeout it refuses typed `AUTHORITY_LOCK_TIMEOUT`, leaves authority unchanged and the operator decides; the S2 drain wait is bounded the same way, and the operator kill path is: identify the holder from the lock file's recorded pid, stop it with the normal process signal, rerun `drain`. Official v2 commits (main commit, outcome import, supersede) are all fenced by `decisions.insert`'s owner check; `_require_catalog_authority` is only the supersede-path guard. `{legacy, 1}` `authority.json` is created by `ops cutover authority init` (slice 1a creates the catalog row, 1b the legacy file; one command, owned by 1a, with 1b adding the file step) before S1. Slice 1b provides the wrapper and files; until then the legacy scheduler is fenced only by disabling it, which the receipt records but the drill treats as insufficient (a restarted scheduler must refuse).
3. **Transfer is two ordered writes, never one.** Fence order is always: (a) fence the *current* writer (it cannot commit any more), (b) verify it is fenced, (c) only then grant the other side. A crash between (a) and (c) leaves **zero** official writers (safe: writes held, last validated read release served), never two. The reverse order is forbidden. **Owner values.** The catalog `owner` is `catalog` (what `ledger import-history` sets, and today the owner that `decisions.insert` requires and defaults to (`engine/v2/ledger/decisions.py`), which fences all official v2 commits; `_require_catalog_authority` in `engine/v2/ops/decision_commit.py` is only the supersede-path guard: the pre-cutover, non-official v2 commit authority used by shadow and scratch runs), `v2` or `none`. The S2b import sets the owner to `catalog` whenever it processes a nonempty file (`ledger_history_import.py`, `_set_authority_once`), so after S2b the owner is `catalog` on the first switch and on a re-switch after a backout (`v2 -> none`) alike; if the import finds nothing to process it leaves the owner as it was: `none` after a backout, or no `decision_authority` row at all on a fresh catalog (then S2b records "no row" and S5 creates the row via `set_authority(conn, None, "v2", stamp)`). S2b therefore records the post-import owner and generation in the boundary receipt, and S5 passes exactly that owner as `expected_owner` (`catalog -> v2`, or `none -> v2` when the import was empty), refusing any other value. S1's owner is informational only. The legacy file starts `{legacy, 1}`; fence writes `{none, n+1}` and grant writes `{legacy, n+2}`; the two generations are independent and only compared within their own record.
4. **Switch receipt.** Each step writes one immutable JSON receipt (step, authority generations before/after, high-water marks, input hashes, result) as `<ops_root>/cutover/<switch_id>/<seq>-<step>.json` using the existing write-once atomic artifact write; an existing name is never rewritten (a retry writes the next `seq`). The ordered set is the log; there is no mutable `receipts.jsonl`. The receipts are what the P7 readiness checker reads; summary booleans are never trusted.

Slice 1a (catalog side) and 1b (legacy files, held for sign-off) provide `python3 -m engine.v2.ops cutover authority {init,status,fence,grant}`; `status` is read-only and is the only authority command the drills use for observation.

## Switch protocol (forward)

Each step is idempotent on `switch_id` (below, R6) and refuses to start if the previous step's receipt is absent or its hashes no longer verify.

## Backout (rollback)

**Triggers** are those in the Phase 7 guide: unexplained economic drift, missing population, duplicate authority, unreconciled decisions, unrecoverable publication, missed session deadline. If facts cannot be reconciled, hold writes (authority stays with nobody) and keep serving the last validated read release.

Backout never restores an old database over new official facts, never deletes a v2 row, and never lets the old scheduler repeat a completed decision.

| # | Step | Command |
|---|---|---|
| B1 | Fence v2 first: `set_authority(conn, "v2", "none", stamp)`; wait for in-flight v2 jobs to reach a terminal state (bounded, default 300 s; on timeout B1 refuses `AUTHORITY_LOCK_TIMEOUT` with authority unchanged and the operator stops or cancels the stuck job through the normal job controls before rerunning); legacy writers acquire the shared `flock` with the same bounded wait and refuse `AUTHORITY_LOCK_TIMEOUT` rather than hang; verify with `status` | `ops cutover authority fence` (slice 1a) |
| B2 | Capture the v2 high-water marks again and diff against the S2b post-import marks (not S1's preliminary ones, which exclude the imported legacy delta): the v2 official decisions/outcomes committed since the switch are the *reconciliation set* | `ops cutover capture --diff` (slice 2) |
| B3 | Reconcile: every committed v2 decision/outcome is exported in the legacy ledger format and appended to the legacy ledger under the exclusive `authority.lock`. The catalog cannot transact a file append, so the boundary is explicit: the batch is first written as a hashed staging file, its lines are appended, then a completion record carrying the batch hash is written to a separate sidecar file (never into the prediction/outcome JSONL, whose readers parse every nonempty line as a ledger record), and the receipt follows the sidecar record. Before any append, B3 re-hashes the staged batch against its recorded hash (mismatch refuses `BATCH_HASH_MISMATCH`) and preflights the whole batch for divergences with the legacy ledger; it records the hash of the lines actually appended in the sidecar record. Crash recovery truncates a torn trailing line and replays the staged batch, appending only ids not yet present (keyed by the deterministic decision id); a v2 decision is never marked void. A divergence between a legacy and a v2 row for the same occurrence is recorded in `decision_divergences` (existing) and the rollback stops for the operator | `ops cutover backout reconcile` (slice 6), built on `engine/v2/ledger/export.py` |
| B4 | Grant legacy: write `authority.json` with the next generation and `owner: "legacy"`, only after B3's receipt verifies | `ops cutover authority grant` (slice 1b legacy file; B3 is the privileged reconcile path that appends while owner is `none`, checking owner `none` and the generation under the exclusive lock) |
| B5 | Re-enable the legacy schedule; switch consumers back to the legacy release; keep v2 read-only | `ops cutover backout resume` (slice 6) |
| B6 | Verify as S8 against legacy; the v2 catalog stays intact as evidence | `ops cutover verify --side legacy` (slice 6) |

## Legacy catch-up

Rollback at session `k` of the 10-session window means legacy missed sessions 1..k, during which v2 was the official writer. The old scheduler resuming is **not** a catch-up: it must not decide those sessions again.

1. **Decisions for missed sessions are taken from v2.** B3 appends them. Legacy treats them as already decided for those occurrences; its scheduler wrapper reads the appended ledger and refuses to emit a decision for an `as_of` that has one.
2. **Settlements**: positions opened by v2 decisions that mature after the rollback are settled by the legacy settlement run like any other open position; outcomes v2 already settled are carried by B3, so nothing settles twice (keyed by decision id).
3. **Sessions where v2 committed nothing** (a missed or held session) stay missed. Legacy does not retro-decide them with stale prices; they are listed in the receipt as `no_official_decision`. This is **new rollback behavior**: legacy backfill is on by default and would call `ledger.snapshot` for missed nights (`engine/dashboard/nightly.py`), and the existing guard in `engine/ledger.py` (and the slice 1b wrapper's "already in the ledger" check) does not cover these sessions. Slice 6 therefore suppresses legacy backfill for every session in the receipt's `no_official_decision` list (a fence-controlled skip set the wrapper reads), with a regression control: after B5 the legacy scheduler run writes no row for such a session.
4. **State and caches** the legacy deployment keeps (price history, calendar, model files): the retained legacy tree and data are not mutated during the window, so they are stale by exactly the missed sessions. The first legacy run after B5 runs its normal incremental data refresh; this is verified in B6 (freshness) and is the one place the window's cost shows. Anything legacy cannot refresh in one run is a rollback blocker the operator sees before B4, because B3's receipt records the data staleness.
5. **Rollback after the window** is not supported: 8A may have deleted the legacy tree. The window closes at one event: the S8 receipt that verifies the tenth completed session after the switch. A backout requested before that receipt exists is allowed; once it exists, `ops cutover backout` refuses and the checker reports the window closed.

## Failure semantics (R1-R6)

Applied to every step above (S1-S8, B1-B6) unless a row says otherwise.

| | S1-S4, B2 (capture, drain, backup, restore verify) | S5, B1, B4 (fence moves) | S6-S8, B5, B6 (start, switch, verify) | B3 (reconcile) |
|---|---|---|---|---|
| **R1 missing input** | A missing or unverifiable prior receipt, backup, legacy copy or restore target refuses with a typed code; no state changed | Missing prior receipt or `status` mismatch refuses; no authority write | Missing release, pointer or receipt refuses | Missing export or legacy ledger refuses |
| **R2 cache** | None. Every read is from the live catalog or a hashed artifact; a cached high-water mark is never accepted | None; `status` is always read live | Consumers' ETags are compared, never trusted from memory | None |
| **R3 retry** | Safe: re-running recaptures and overwrites nothing (new receipt appended, earlier kept); a changed mark is reported, not merged | Retry resumes from the observed owner/generation; never grants if the other side is not verified fenced | Retried by `switch_id`; the schedule is started at most once per generation | Retry re-runs the diff and appends only missing ids |
| **R4 transaction** | Backup is atomic by its own contract; capture is one read transaction | `set_authority` is one catalog transaction (compare-and-swap); the legacy `authority.json` write is atomic rename | Pointer swap is atomic (`os.replace`); schedule start is a single enable | Catalog reads are one transaction; the file append uses the staged-batch and sidecar-completion boundary above, and the receipt follows the sidecar record |
| **R5 partial write** | A partial backup is not accepted: completeness is the verified backup manifest, published last; the restore drill also hashes the result; partial scratch is removed or kept as diagnostics | A crash between fence and grant leaves **no** writer; it is detected by `status` and finished or reversed by an operator command | A crash after the pointer swap but before the receipt: re-run `verify` first completes or confirms the retained publication's durable acknowledgement (release row, outbox delivery, watermarks; a valid pointer alone does not replace it) and only then records success; no second swap | A crash mid-batch leaves a torn line or some ids appended; recovery truncates the torn line and replays the rest; rows are never deleted |
| **R6 idempotency** | `switch_id` + step name keys the receipt; a rerun is a no-op when the hashes match | Fencing an already-fenced writer or granting an already-granted side is a no-op, a grant to the wrong generation refuses | As S5 | Keyed by decision id; a duplicate append is a no-op, a differing payload is a divergence and stops |

**Legacy moves after S2b.** Legacy stays the authority until S5 writes `authority.json`, so a hand-started legacy run after S2b could commit decisions the catalog never imported. S2 therefore also fences legacy's scheduler (disabled) and S5 re-reads the legacy counts and tail hash immediately before the fence write, under the exclusive `authority.lock`, and refuses `BOUNDARY_STALE` on any mismatch with the S2b receipt (no authority write; the operator reruns S2b). The new negative control below covers it.

**S2b is not read-only** (it is excluded from the first column's "read transaction"/"no state changed" entries). It runs `ops ledger import-history`, which commits per source file. Conditions and outcomes: a failure mid-import leaves earlier files committed and later ones not; no boundary receipt is written; a retry is idempotent by source hash and line, so it appends only what is missing; repeated legacy rows that differ from catalog rows still import (the importer records them as divergences per the standing 2026-09-14 rule and does not block); what refuses is a catalog-vs-legacy count or tail-hash mismatch after the import, or an `IDEMPOTENCY_CONFLICT`, and it writes no boundary receipt. On a re-switch, B3-exported legacy lines are re-imported by S2b and must match their catalog rows by payload hash (they are keyed by the same decision id); a mismatch is recorded as a divergence and listed in the boundary receipt but, as on the first switch, does not refuse (one rule for both: divergences are recorded and reported, never blocking; only a count or tail-hash mismatch or `IDEMPOTENCY_CONFLICT` refuses), and S3-S5 refuse without one. The importer's authority move (`catalog` set when it processes a nonempty file) is itself fenced, see slice 1a.

R1 also covers the authority and receipt file reads: no-follow, regular-file, byte-capped, refusing `AUTHORITY_FILE_INVALID` on a missing, oversize or malformed file. S5 compares the catalog generation as well as the owner against the S2b receipt (a changed generation refuses `BOUNDARY_STALE`).

Cross-cutting: no receipt, log or artifact carries a local path or raw exception text (`ARCHITECTURE.md` §5); the typed code and the operation id are enough to find the private diagnostic.

## Negative controls and expected outcomes

Each is a scenario for `tools/v2_controlled_failure_drill.py` (existing scenarios `after-good-release`, `before-any-release`; slice 7 adds all seven controls below) or the P7-3 checker, with a `fault=` hook at the named point. The drill target is a scratch copy; #740's planned separate scratch catalog for native shadow decisions is a dependency, not an existing capability: it has no producer yet. Until it lands, slice 7 provisions the rehearsal target itself (a scratch catalog seeded with synthetic decisions, as the controlled-failure drill already does for its fixtures); once #740 lands, slice 7 switches to it where it fits. Either way the controls need no private data.

| Control | Fault | Expected outcome |
|---|---|---|
| **Interrupted switch** | Kill after S5's fence step, before its grant step; then, separately, after the grant but before S6 | First: zero writers, no commit possible from either side, `status` reports legacy file owner `none` while the catalog owner is still `catalog` (neither side can commit), consumers still on the last validated release; operator re-runs `grant` or `fence` and the switch completes or is abandoned. Second: v2 owns but no schedule; re-running S6 starts it once. In neither case do two writers exist; both writers attempting a commit are refused in the first case |
| **Rollback before any official commit** | B1-B6 immediately after S6 with no v2 official row | Reconcile set is empty; legacy resumes; the receipts show B2 marks equal to the S2b post-import marks; v2 decision and outcome facts unchanged (only authority metadata differs, owner `none` and a higher generation, and is verified) |
| **Rollback after one official commit** | Commit exactly one v2 decision and one outcome, then B1-B6 | B2 shows 1 decision, 1 outcome; B3 appends them to the legacy ledger; legacy does not re-decide that occurrence; v2 rows still present and identical; ledger counts equal the S2b post-import marks + 1; a pointer-only rollback in the same scenario fails the check (the legacy ledger lacks the row), which is the proof a pointer rollback is not ledger recovery |
| **Legacy run after S2b** | After S2b, append one legacy ledger row by hand, then run S5 | S5 refuses `BOUNDARY_STALE` before any authority write; owners unchanged; rerunning S2b imports the row, writes a new boundary receipt, and S5 then succeeds |
| **Duplicate writer** | After S5, start a legacy scheduler run, a direct `engine/ledger.py` append, a manual legacy `publish_bundle` run and a stale v2 job from generation N, a v2 `publish_local` without owner `v2`, plus (staged setup: run B1-B4 so legacy is re-granted, then start a legacy survivor from the earlier generation) an `ops ledger import-history` run | Each of the four legacy-side writers (scheduler wrapper, direct `engine/ledger.py` append, `publish_bundle`, and a legacy survivor re-granted after a backout) refuses `AUTHORITY_FENCED` (owner mismatch) or `AUTHORITY_GENERATION_STALE` (survivor), with zero rows or bundles written and the exact code asserted; the import-history run refuses `AUTHORITY_FENCED` with the owner unchanged and the generation not bumped; the stale v2 job's commit is refused `AUTHORITY_GENERATION_STALE` by the generation check inside its transaction; zero rows written; refusals appear in the receipts |
| **Reconcile divergence** | Legacy ledger already holds a differing row for a v2-decided occurrence | B3 records a `decision_divergences` row, appends nothing for that id, stops with a typed refusal; authority stays owner `none` |
| **Backout past the window** | Write the session-10 verifying S8 receipt, then request rollback | Refused: window closed |

## Slice list

Each slice is one PR of at most about 400 non-test code lines, with tests in `tests/v2/ops/` and no heavy run by the owner.

1a. **v2 authority fence** (code only in `engine/v2`): the importer's authority move (`ledger_history_import.py`) may move authority only from `catalog`, from `none` or from no row, and refuses `AUTHORITY_FENCED` when the owner is `v2`; `decisions.insert` and its callers (`decision_commit.py` main commit and outcome import, `ledger_history_import.py`) pass an explicit `official` flag: an official insert is accepted only with owner `v2` and the generation captured in the job record (`AUTHORITY_FENCED` otherwise, `AUTHORITY_GENERATION_STALE` on mismatch), never redirected, so before S5 v2 cannot make official commits at all (pre-switch v2 commits, shadow runs, and the S2b history import are non-official and keep working under `catalog` or `none`; this closes the fence-to-grant gap); `publish_local` (`engine/v2/ops/publication.py`, the `CURRENT` pointer write) and `publication_effect` (`engine/v2/ops/effects_graph.py`) are fenced the same way for the official scope only, refusing `AUTHORITY_FENCED` without owner `v2`; non-official scopes (`shadow`, the drill's scratch scope; non-official owners are `catalog`, `none` and `drill`) are exempt, with a control that a shadow publish under `catalog` still succeeds; the supersede guard's existing `VALIDATION_FAILED` becomes `AUTHORITY_FENCED` (not retryable); the legacy inventory also decides whether the calibration state writes at `engine/ledger.py` are official; `ops cutover authority fence/grant` here act on the catalog only, the legacy file writes arriving with 1b; `switch_id` is minted once by `ops cutover capture` (UUID), recorded in the first receipt and reused on every retry; the supersede guard and `session_backfill.py`'s `UPDATE decisions SET generation_ref` get the same owner check; `AUTHORITY_LOCK_TIMEOUT` is owned here (refusal, not retryable, authority unchanged); `ops cutover authority {init,status,fence,grant}`; each refusal has a test. S1/S5 legacy count/hash and S2b/S3 legacy reads stream line by line (or refuse `IMPORT_INPUT_TOO_LARGE` (defined here, asserted in slice 7) before reading), never loading a whole file.
1b. **Legacy authority fence** (held for the #739 sign-off): `authority.json` + `authority.lock` + scheduler wrapper, and the direct append sites in `engine/ledger.py` (both `mode = "a" if path.exists() else "x"` appenders), `publish_bundle` in `engine/dashboard/publish.py` and every other legacy writer of official rows, exports or published bundles found by inventory; each takes the shared lock, re-reads `authority.json`, checks owner `legacy` and records the generation at start, re-checking it under the lock before each append (a survivor of a backout and re-grant refuses `AUTHORITY_GENERATION_STALE`); opens use `O_NOFOLLOW|O_NONBLOCK` then `fstat` regular-file and size cap before lock or read.

4. **Official nightly mode**: `official` mode in `plans.nightly_plan` (and the `build_nightly_plan` test path) with production CLI/trigger/submission wiring, gated on a fresh S5 receipt and generation.
